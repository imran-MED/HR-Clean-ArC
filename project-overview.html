An HR back-office tool that authenticates Qassim University staff against the central HaramAPI identity service, then delivers an employee directory, attendance reconciliation, rosters and role management through an RTL Arabic single-page app.

What it does

Core Features

Four functional pillars, each backed by a use-case service in the Application layer and exposed through a dedicated REST controller.

🔐

Authentication

Logs users in against the external HR identity API (hrapi.qm.edu.sa), manages token refresh & validation, and keeps a local audit row per employee. Passwords are never stored — identity is delegated. Auto-logout after 10 min idle.

👥

Employee Directory

List, search & filter employees by position, add them manually or via CSV import (≤10 MB, auto-delimiter), and sync each employee's position & supervisor from SmartHCM.

🕒

Attendance Reconciliation

Three sources — uploaded punch exports, SmartHCM daily summaries, or raw Oracle punches — matched against rosters to flag late arrivals, early departures & missing periods with per-position grace margins.

📅

Rosters

Per-employee shift roster lookup by date, sourced from SmartHCM and cached locally. Rosters drive the attendance matching engine.

🗂️

Roles

Full role-catalog CRUD and assignment of roles to employees, stored as PostgreSQL text[] arrays on each employee record.

🌴

Leaves

Fetches an employee's pending leaves from SmartHCM, stores them locally, and feeds reconciliation so days on approved leave aren't flagged as absences.

How it's built

Clean Architecture — 4 Layers

Dependencies point strictly inward. The Application layer defines ports (interfaces); Infrastructure supplies the adapters; Program.cs wires them at startup. Cross-layer outcomes use a Result<T> type instead of throwing.

HrAuth.WebApi entry point
Controllers (Auth · Employees · Attendance · Roles · Roster), Program.cs DI/CORS/Swagger, and the static Dawam SPA in wwwroot.
▼ depends on
HrAuth.Infrastructure adapters
EF Core repositories, the HrAuth REST client, SmartHCM ASMX / Oracle providers, crypto & migrations. Implements the ports.
▼ depends on
HrAuth.Application use-cases + ports
Services (Authentication, Employee, Reconciliation, Roster, Role), port interfaces (IHrAuthProvider, I*Repository), DTOs & Result<T>.
▼ depends on
HrAuth.Domain no dependencies
Entities & domain rules: AuthSession, AuthenticatedUser, AttendanceRecord, Roster, EmployeeId normalization.

Integrations

External APIs & Services Used

HrAuth orchestrates several external systems through ports, choosing a provider based on which credentials/connection strings are configured.

🛡️

HaramAPI — HR Identity

POST https://hrapi.qm.edu.sa/api/hr/auth/*

The authoritative identity provider. Handles login, refresh-token and validate-token. Optional secure-client mode via an X-Hr-Login-Gateway-Token header. Responses parsed defensively (snake_case & camelCase tolerant).

🏢

SmartHCM Web Service

https://hr.qm.edu.sa/ws/SmartHCMWS.asmx

SOAP/ASMX service for employee directory, positions, supervisors, rosters and daily attendance summaries. Authenticated with a token key + security key and an admin employee credential.

🗄️

Oracle Database

Oracle.ManagedDataAccess.Core 23.6.1

Direct access to raw attendance-machine punches and an alternative employee directory source, used as a fallback to the SmartHCM API.

🐘

PostgreSQL

Npgsql + EF Core 9.0.4

The app's own store — employees, attendance_records, reconciliation_runs & roles. Uses native text[] arrays and jsonb. Migrations applied on startup (best-effort).

⚙️ Provider selection is conditional: directory/attendance data comes from the SmartHCM API → Oracle → ASMX fallback depending on which credentials are present (see Infrastructure/DependencyInjection.cs).

End to end

Authentication Flow

How a login request travels from the Dawam SPA through the layers to the external identity API and back.

1
Dawam SPA → POST /api/auth/login

Browser sends { userName, password } to the Web API.

2
AuthController → AuthenticationService

Controller delegates to the use-case service in the Application layer.

3
IHrAuthProvider.LoginAsync()

Port call → HrAuthProvider POSTs to https://hrapi.qm.edu.sa/api/hr/auth/login (optional gateway-token header).

4
Parse → AuthSession + audit

HrAuthSessionParser builds the domain session; EmployeeRepository.UpsertAsync writes a local audit row (first seen / last login). No credentials stored.

5
← AuthResult to browser

Returns access/refresh tokens, expiry, user id, display name & roles. SPA stores it in sessionStorage and navigates to the dashboard.
